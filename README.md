# Стенд пресейл-агента Softline

Хакатонный прототип. Каталог и база знаний хранятся в SQLite с FTS5.
Не добавляйте исходные выгрузки, базу, КП и `.env` в Git.

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
python -m unittest discover -s tests -v
python -c 'from app.config import Settings; from app.db import initialize; initialize(Settings().db_path)'
```

При старте без ключей не следует обращаться к боевым сервисам. Значения секретов вводятся локально.

## Индекс каталога и базы знаний

Проверка на ограниченной выборке (XML или gzip, формат определяется по содержимому):

```sh
python -m scripts.build_db --feed ../FeedStore.yml.gz.xml --limit 50 --db data/sample.db --fetch-kb
```

`--fetch-kb` загружает только отсутствующие страницы; повторную сборку можно выполнить
с `--kb-cache raw_data/kb_cache` без доступа к сайтам. Записи менеджеров не удаляются.
Эмбеддинги строятся через FastEmbed на CPU. При первом запуске E5 скачивает ONNX и токенизатор;
для проверки без ONNX добавьте `--fts-only` и используйте отдельную БД: этот флаг
записывает выбранные строки **без** эмбеддингов. `--limit` ограничивает чтение фида,
но не удаляет строки, уже существующие в БД.

`app.db.search_catalog(conn, query, embedder=E5Embedding(), synonyms=...)` и
`app.db.search_kb(conn, query, embedder=E5Embedding())` объединяют FTS5/BM25 и
косинусное сходство через RRF. Переиспользуйте один экземпляр `E5Embedding`.
`search_catalog` сначала выводит точные совпадения артикула с исходным запросом,
даже если синоним изменил текст для FTS5. Без `embedder` или готового `query_vector`
семантическое ранжирование отключено. Пустой запрос в `search_catalog` с `group_id`
возвращает варианты этой группы.

## Артефакты из маскированных обращений

```sh
python -m scripts.mine_chats
```

Майнер локально читает только `buy_part_{1,2,3}_masked.txt` из соседнего
`support_chat/`. Он не использует сеть, LLM, фид или БД. Результат — три JSON
в `data/mined/` (каталог игнорируется Git, регенерируется перед запуском):

- `eval_set.json`: по умолчанию 28 уникальных запросов, каждый построен из одного
  реального обращения. Сохраняются код исходной категории, распознанные намерения,
  известные названия продуктов и признаки слотов. Текст запроса составляется
  из фиксированных фраз, а не из фрагментов клиента; ID, URL, имена, реквизиты
  и пользовательские значения не копируются. Сначала подбирается по одному
  различному тексту для максимального числа исходных тегов. Если один текст
  получился из строк с разными тегами, он может представлять только один тег;
  майнер пробует переназначить общий текст, а если разных текстов на все теги
  не хватает (или лимит ниже числа тегов), часть тегов останется без кейса.
  При подборе приоритет у статуса заказа и доступности зарубежных вендоров;
  свободные места сначала дополняют эти сценарии до двух кейсов каждого, если
  хватает разных текстов, затем балансируются по тегам и разнообразию признаков.
- `synonyms.json`: четыре нормализации из ТЗ плюс варианты из закрытого списка,
  встретившиеся хотя бы в двух строках вне eval. Строка учитывается один раз,
  только если вариант встретился вне всех точных вхождений канонического имени
  (без учёта регистра): `Astra Linux` само по себе не даёт голоса за `astra`.
  Поиск по каталогу читает этот файл при `synonyms=None`; отсутствие файла
  отключает подстановки. Явный словарь переопределяет файл, а `synonyms={}`
  отключает его чтение.
- `slot_playbooks.json`: 3–4 вопроса для каждой группы (`os`, `scanner`, `office`,
  `mail`). Поле `mentions` — число строк вне eval с названием продукта группы
  и данным признаком; 0 означает вопрос из ТЗ/эвристики без подтверждения в выборке.

При подсчёте исключаются все строки, дающие выбранный eval-текст, независимо
от исходного тега. В локальной выборке из 495 строк получены 28 разных текстов
по всем 9 тегам (нет общих текстов между тегами), в том числе один различимый
кейс статуса заказа и восемь кейсов доступности зарубежных вендоров. Вне eval
остались 313 строк; получены 8 синонимов и 4 плейбука. У всех вопросов почтового
плейбука `mentions=0`: это заготовки, а не подтверждённые корпусом вопросы.

Это выборка для проверки сценариев, не случайная оценка трафика и не размеченный
набор правильных ответов. Шаблоны не сохраняют исходные опечатки, точные SKU
и значения слотов; для проверки нормализации и сохранения SKU используются
отдельные тесты поиска.

## Ядро агента и КП (этап 4)

На старте вызовите `app.db.initialize(settings.db_path)`: это обновит схему без
пересоздания БД. Создайте `AgentTools(settings, embedder=...,
send_file=..., redirect_chat=...)` и один `Agent(settings, tools)`; при остановке
вызовите `await agent.aclose()`. Передайте существующий чат и историю текста в
`await agent.run(chat_id, history)` и отправьте возвращённый текст. `None` означает,
что бот не должен отвечать. Для гибридного поиска передайте общий `E5Embedding`;
без него используется FTS. `send_file(chat_id, public_url)` и
`redirect_chat(chat_id)` — асинхронные callbacks транспорта, не HTTP-маршруты.
Транспорт должен сериализовать ходы одного чата.

На все ходы модели и поисковые инструменты одного запроса выделено 90 секунд,
не более 5 вызовов LLM. Запросы к модели ограничены 24 000 байтами сообщений
и 1024 токенами ответа; больший контекст сокращается с сохранением связанных
вызовов и результатов. На процесс допускается один поисковый инструмент за раз;
если он занят, следующий получает `SEARCH_BUSY` без постановки в очередь. По
отмене SQLite прерывает выполнение запроса через progress handler, а векторный
поиск не начинает следующий пакет. Уже начатый вызов E5 или нативная операция
NumPy не прерываются извне: слот остаётся занятым до фактического выхода
поискового потока. Транспортные callbacks имеют отдельный таймаут в 8 секунд.
Если локальная эскалация записана, но редирект не подтверждён, следующий вызов
`agent.run` повторяет только редирект, без модели и без новой эскалации.
Без `redirect_chat` эскалация остаётся локальной. Callback редиректа должен быть
идемпотентным: внешний результат может быть неизвестен после таймаута.

Подтверждение проходит **вне LLM**: интерфейс получает `tools.pending_quote(chat_id)`,
показывает точный состав и условия и связывает кнопку клиента с `confirmation_id`.
После проверки принадлежности чата он вызывает `tools.confirm_quote(chat_id,
confirmation_id)`; при `True` запускает следующий ход агента для выпуска КП.
Не вызывайте подтверждение по тексту «да» или со слов модели. Изменение состава,
цен, скидки или условий не использует старое подтверждение. Стандартные условия —
предоплата и сроки по условиям вендора; особые условия уходят менеджеру.
Подготовленное или выпущенное КП завершает ход независимо от номера шага.
Автоматическое КП ограничено 12 позициями, 1 млн единиц на позицию и 10 млрд руб.
Точная сумма новых КП хранится в `quotes.total_sum_kopecks`; `total_sum` остаётся
для совместимости. Для старых записей точное поле остаётся `NULL`.

PDF создаётся в `pdfs/` рядом с `DB_PATH` (`data/pdfs/` по умолчанию). Для проверки PDF
на Windows можно указать `STAGE4_TEST_FONT_DIR` с двумя файлами DejaVu Sans и добавить
`pdftotext` в PATH. На сервере шрифты берутся из `FONT_DIR`. Проверка поведения
LLM использует тестовый клиент и не требует ключа.

## Webim Smart Bot 2.0 (этап 5)

Запуск: `python -m uvicorn app.main:app --workers 1 --no-access-log`. Локально
задайте два разных секрета `WEBIM_WEBHOOK_TOKEN` и `WEBIM_BOT_TOKEN` в `.env`;
без них соответствующие маршруты закрыты. По умолчанию клиент вызывает
встроенный Mock-Webim через HTTP/ASGI, без внешней сети. Для подключения
[боевого Webim](https://webim.ru/kb/bots/smart-bot/v-2-0.html) укажите HTTPS-origin
аккаунта в `WEBIM_BASE_URL`, токен бота в `WEBIM_BOT_TOKEN`, а в настройках Webim —
публичный HTTPS URL `/webhook/webim/<WEBIM_WEBHOOK_TOKEN>` (секрет из URL нельзя
писать в access-логи, в том числе на прокси). Для локальных вызовов можно вместо
секрета в пути передать `Authorization: Token …` на `/webhook/webim`.
В режиме стенда не проксируйте `/mock-webim/` наружу; приложение также проверяет
loopback-адрес клиента и токен бота.

`new_chat` принимает накопленные сообщения, `new_message` — отдельное сообщение.
Только аутентифицированный `new_chat` может вернуть переданный чат боту: нужен
тот же `visitor.id` (если уже известен) и новый ID текстового сообщения посетителя
или первый пустой `new_chat` для этого чата. В Webim v2 нет ID/времени назначения:
повторный пустой callback и callback только с уже известными текстовыми сообщениями
неотличимы от старой доставки и не меняют владельца. Закрытые чаты не возобновляются.
HTTP `200 {"result":"ok"}` подтверждает запись, не готовность ответа. Бот отвечает
только на новый текст посетителя. Одна очередь на чат сохраняет порядок приёма
в SQLite; завершённые и дублированные ID не запускают модель. После перезапуска
ожидающие сообщения читаются из SQLite; ход, уже начатый до аварийной остановки,
не переигрывается, чтобы не повторить внешний эффект. Для нескольких процессов
потребуется межпроцессная координация очередей.

В `audit_log` сохраняется структура v2 и результат доставки без текста, URL,
контактных полей и токенов; рабочая переписка хранится отдельно в SQLite.
`PUBLIC_BASE_URL` должен быть доступен серверу Webim для загрузки файла. Ссылка на
зарегистрированное КП доступна любому, кто её получил, и не имеет срока действия;
листинга и выдачи незарегистрированных файлов нет.

## Split-screen стенд (этап 6)

Запускайте на loopback и с отдельной БД (`DB_PATH=data/demo.db`), не с рабочими
чатами. Задайте `DEMO_ENABLED=true` и три разных локальных секрета:
`WEBIM_WEBHOOK_TOKEN`, `WEBIM_BOT_TOKEN`, `MANAGER_TOKEN`. Оставьте loopback
`WEBIM_BASE_URL` с `/mock-webim`, запустите `python -m uvicorn app.main:app
--host 127.0.0.1 --workers 1 --no-access-log`, откройте `/`. В правой колонке
токен менеджера вводится отдельно и остаётся только в памяти вкладки.

1. Спросите «Как оформить тестовый пилот?». Без LLM неизвестный вопрос
   переводится менеджеру через Mock-Webim. Ответьте на эскалацию: реплика
   появится в клиентском чате, а факт отправки — в аудите.
2. Нажмите «Оформить ответ и добавить в БЗ», проверьте текст и подтвердите
   публикацию. Черновик не участвует в поиске, публикация атомарно обновляет
   SQLite и FTS. Откройте новый диалог и повторите вопрос.
3. С `DEMO_EMBEDDINGS=true` и доступным локальным E5 публикация вычисляет
   вектор до коммита SQLite; тот же экземпляр поиска видит статью сразу.
   Если вычисление не удалось, черновик не публикуется. По умолчанию — FTS.

Без `LLM_API_KEY`/`LLM_MODEL` черновик лишь копирует обезличенные вопрос и ответ;
офлайн-агент отвечает только на точный вопрос из опубликованных демо-Q&A.
С LLM черновик формируется через `LLM_FAST_MODEL` (или `LLM_MODEL`); текст всё
равно требует явного подтверждения. КП в режиме LLM требует данных каталога,
шрифтов и подтверждения показанного состава клиентом перед выпуском PDF.

`/api/demo/chats` выдаёт случайные ID и отдельные capability-токены;
`/api/manager/*`, включая инспектор, требует `Authorization: Token <MANAGER_TOKEN>`
и обслуживает только демочаты. В режиме стенда внешние callback не принимаются:
UI использует тот же валидатор и FIFO Webim внутри приложения, а ответы/редиректы
идут через HTTP/ASGI в Mock-Webim. Инспектор отдаёт структурную проекцию, не
сырые тела пакетов. Используйте только вымышленные тексты: фильтр адресов и
телефонов не распознаёт все персональные сведения. Общий токен не идентифицирует
сотрудника и не предназначен для production.

В экономике запрос — один ход агента, а не отдельный вызов LLM. Средние
считаются только по ходам с измерением; стоимость в USD доступна с обоими
заданными тарифами, в ₽ — дополнительно с `USD_TO_RUB`. Неизвестные значения
не заменяются нулями; генерация черновика учитывается отдельным типом аудита.
